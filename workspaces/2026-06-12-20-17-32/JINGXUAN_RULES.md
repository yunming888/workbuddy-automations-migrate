# 头条精选·发布规则（v1.1，2026-09-12 改版 RC4/RC3）

## 一、核心变更

旧规则作废：**每天固定产出 N 篇板块文案、只产不发布**。
新规则：**只有抓到后台新推送的、且从未发过的「头条精选」条目，才写才发；没抓到新的就一条都不发。**

am / pm 两档共用同一套脚本、同一个状态文件、同一段判定逻辑，不按时段做分支。

## 二、去重判断依据（唯一）

- **状态文件**：`jingxuan_state.json`（工作目录根，由 `jingxuan_sync.js` 读写，am/pm 共用，禁止另建状态）
- **条目标识**：文本指纹 `fp` = `sha1(条目文本归一化后前 24 字符).slice(0,12)`
  - 归一化 = 去 emoji / 去标点 / 去空白
  - 取前 24 字符而非全文，是为了容忍同一热点后半句措辞微调，避免"换个标点就当新热点"
- **状态字段**：
  | 字段 | 含义 |
  |---|---|
  | `sent` | 是否已成功发布。**true 则任何时段都不再发**，这是杜绝重复的唯一闸门 |
  | `sent_at` | 发布时间 |
  | `slot` / `file` | 由哪个时段、哪个文件发出去的，便于回溯 |
  | `attempts` | 连续失败次数，上限 3，超过不再自动重试（转人工） |
  | `push_at` | 后台推送时间（形如 `09-07 20:27`） |
  | `first_seen_at` | 首次被抓取到的时间 |

## 三、判定流程（两档逐字一致）

```
node jingxuan_sync.js --check --slot <am|pm>
```

**🟢 数据源（RC4，2026-09-12 根治）**：抓取**优先拦截 `bcs/notice/cell/list/?app_id=1231` 接口读 JSON**（`cells[].content.body.text` = 「今日大家都在关注」整块，`create_time` unix 秒→北京时间即 push_at），innerText 正则仅作兜底。
> ⚠️ 精选**不在** `api/msg/v1/list`（那条恒返回空 `msg_list:[]`，183 字节，找不到精选别在这条接口上找）。cell/list 还能**复抓到被新通知顶出可见区的旧精选** → 天然解决"孤儿漏发"（如 09-11 缝纫自习室 `f61ff498b587`）。
> 日志会多打两行：`API_OK=0/1`、`API_CELLS=n`；`src=api` 表示走接口，`src=innerText` 表示兜底。

**退出码**：

| 退出码 | stdout | 动作 |
|---|---|---|
| 3 | `NO_NEW_JINGXUAN` | 本次抓到的精选全部已发过 → **不写稿、不发布**，汇报写「头条精选：无新增，跳过」。这是正常结果，不是失败 |
| 3 | `NO_JINGXUAN_CROSS_SLOTS` | **抓取正常（页面渲染 OK），但可见列表里没有「头条精选」推送** → 时点让位，不写稿、不发布、**不告警**，汇报写「头条精选：本档无精选，交另一档兜底」。这是"晚抓不到早抓"的跨档对冲出口 |
| 0 | `NEW_JINGXUAN batches=… n=…` | **RC3**：按 `BATCH push_at=…` 分批输出。本档把列出的 pending **全部消化**（每个 FP 一条原创微头条，slot 依次取 `<slot>2/<slot>3` 顺延）；不局限于"只发第一条"，避免同批兄弟条目永久悬置成孤儿 |
| 7 | 抓取失败（接口无精选 cell 且页面 len<500 / 未渲染出正文） | **告警，不要当成"无新增"静默跳过**。汇报写「头条精选：抓取失败，已跳过」 |

> ⚠️（2026-09-12 修订）"没有精选"拆成两种：抓取**成功**但列表里没有精选 = `exit 3`（`NO_JINGXUAN_CROSS_SLOTS`，正常让位）；只有页面**真抓取失败/空壳**才 = `exit 7`（告警）。因为精选约当晚 20:00 推，pm(19:00) 此刻多半还没到点，或已被新通知顶出可见区 → 让位给次日 am(07:00) 兜底，两档共用 `jingxuan_state.json` 去重，最终一定被消费。旧逻辑把"时点让位"误判成 `exit 7` 抓取故障，导致天天误告警，现已修正。

拿到 FP 之后（**RC3：本档列出的 pending 全部消化**，逐个 FP 各发一条原创微头条，slot 从 `<slot>2` 起顺延 `<slot>3`；不要再"只发第一条"留孤儿）：

1. 对**每个 FP** WebSearch 补权威事实（发布机构、时间、具体数字、影响范围）——**不补不许动笔**；数字逐条列出处，查不到就不写。
2. 写成一条**原创微头条** 200~500 字：开头两句抓注意力（反差/痛点/具体数字/悬念），结尾留评论钩子，落职场读书视角。
3. **必须调 humanizer skill 去 AI 味**：重点清四类——①三项/四项书面排比 ②"不是A而是B"否定并列 ③被动式+宏大空结尾 ④公文腔套话。
4. 发布（加发档槽位，必须显式传 WT_SLOT / WT_DATE，否则台账闸门按 (date,slot) 判重跳过）：

```bash
taskkill /F /IM chrome-headless-shell.exe
WT_SLOT=<slot>2 WT_DATE=<DATE> node wt_publish.js 'toutiao_wt_auto_DATE_<slot>2.md' '#上头条 聊热点#'
```

5. **发布成功后立刻登记**（顺序铁律）：

```bash
node jingxuan_sync.js --mark-sent --fp <FP> --slot <slot>2 --file <文件名>
```

6. **发布失败则**（不置 sent，下一次运行会再挑出来，保证不漏发）：

```bash
node jingxuan_sync.js --fail --fp <FP>
```

🚨 **先发布成功、再 mark-sent**。反过来做会导致：发布失败却已被标记，这条永久漏发。

## 四、为什么这样既不重复也不漏发

**不重复**：`sent=true` 是全局的，不区分 am/pm、不区分哪天。任何时段抓到同一 fp，只要 sent 为 true 就直接跳过。即便 am 和 pm 抓到的是同一条推送（很常见，因为精选约 20:00 后才推，am 抓到的就是昨晚那条），也只有先跑的那一档发得出去。

**不漏发**：
- 抓取阶段只写 `first_seen_at`，**不写 sent**。抓取过但没发出去的条目，下次仍会作为 pending 被挑出来。
- 只有 `wt_publish.js` 真实发布成功（日志 `REAL_CLEAR= true`）之后才 mark-sent。
- 发布失败只加 `attempts`，条目保持 sent=false → 下一轮自动重试，最多 3 次；超过 3 次转向人工告警，不会无限重试刷屏。
- 抓取失败退出码 7 与"无新增"退出码 3 严格区分，避免把抓取故障误判成"今天没新东西"而永久漏掉。

## 五、常用命令

```bash
node jingxuan_sync.js --show                      # 打印全部条目与 sent 状态（不开浏览器）
node jingxuan_sync.js --check --slot am           # 判定
node jingxuan_sync.js --mark-sent --fp <fp> --slot am2 --file <file>
node jingxuan_sync.js --fail --fp <fp>
```

日志落在 `debug/jingxuan_sync_<日期>.log`。

## 五·B、最新精选"第一时间发"（v1.2，2026-09-28 用户定规则）

**长期规则：只要确认有"未发过"的新精选，第一时间发，不等下一档兜底。** 这是对本文件"退出码 3 / 跨档让位"的**用户级覆盖**——让位逻辑只在"接口确实还没推、无新条目"时成立；一旦有新精选（哪怕接口因时滞暂未追上、只有服务通知看到了原文），不再"留待 am 兜底"，当场补发。

**触发场景（接口时滞）**：头条精选约当晚 20:00 才推，pm(19:00) 档 `--check` 常抓不到、只看到旧的 5 条全 sent（exit 3）。但服务通知里可能**已出现新一对**精选（如 09-28 16:27 推"新秘书长五常/内塔尼亚胡中东"，接口 20:27 仍未追上）。此时：

1. **判定"新"**：`grep '关键标题词' jingxuan_state.json` 无命中 = 该条从未发过 = 新。
2. **手动占位登记 fp**（接口追不上就自己算，算法必须与 `makeFp` 完全一致）：
   ```js
   // norm：去 emoji + 去所有 \s/\p{P}/\p{S}；fp = sha1(norm(标题).slice(0,24)).hex.slice(0,12)
   // 写入 state.items[fp] = {fp,title,push_at,first_seen_at,sent:false,attempts:0,source:"manual_user_named"}
   ```
   ⚠️ 占位的 fp 必须用**同套算法**算，否则将来接口追上来会**重建不同 fp**，导致同一热点被发两次。
3. **WebSearch 补权威事实 → 写成 200~500 字原创微头条（落职场读书视角）→ humanizer 去 AI 味**（同 RC3 流程第 1~3 步）。
4. **发布**（加发档槽位显式传 WT_SLOT/WT_DATE；活动通知已占 pm3，故手动补精选走 **pm2**）：
   ```bash
   WT_SLOT=pm2 WT_DATE=<DATE> node wt_publish.js 'toutiao_wt_auto_<DATE>_pm2.md' '#上头条 聊热点#'
   ```
5. **发成功后才 `--mark-sent`**（顺序铁律不变）；另一条留作下次，避免一堆积压。

**与旧规则的关系**：本条是"用户点名/确认有新版"场景下的**主动补发**，不改变 am/pm 自动档的让位判定；自动档仍按 exit 3 正常跳过，只有人为确认有新精选时才走本节补发。
