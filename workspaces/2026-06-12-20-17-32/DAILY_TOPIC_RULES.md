# 三档（am/noon/pm）选题同步与差异化规则 v1.1

> 生效：2026-09-06 起，am（07:00）/ noon（12:00）/ pm（18:00）三档**同时适用**，规则完全一致。
> 单一来源：本文件 + `daily_topic.json`（当日状态） + `topic_sync.js`（读写/自检工具）。
> 本文件是「内容规则」，原 automation prompt 里的发布/核验/合规条款一律不变，本规则只覆盖**选题与成稿差异化**环节。

## 〇、最高优先级：后台推荐什么就写什么（2026-09-29 用户定，三档 am/noon/pm 固定）

> 本节覆盖下方第一~三节里「写哪一条」的旧逻辑（旧「最新+热度最高重排 / 写过类似就跳过」作废）。
> **只改"选哪条"，不改安全闸门。**

1. **选题 = 触发时后台「为我推荐的」（消息中心「话题邀请」小助手带流量扶持的主推卡片）当前帧原文，能抓到就按它写**：
   - 不做热度重排（不再靠"最新+最热+扶持"筛）；
   - 不做 7 天去重规避（当前帧就是老题也照写）；
   - 不做二次筛选（不凭垂直度/疲劳度自行挑）。**唯一例外＝客观围观量门槛，见第 5 条**：同池内优先取围观量 >10万 的，锚点本身 ≤10万 才在同池改取 >10万 最高一条。
   - 🔴 **执行入口（2026-09-29 起，noon/pm 必跑）**：`node hot_push_grab.js`（只读，落 `hot_push_state.json`），选题锚点 = `recommended.topic`（`support=true`）。读取器故障 / 无为我推荐 → 按 `HOT_PUSH_SOP.md` 第五节退出码分支走三级兜底，**不得编造、不得用隔夜 state**。全流程见 `HOT_PUSH_SOP.md`。
2. **"为我推荐的"怎么取（第一优先级，2026-09-29 用户澄清）**：选题锚点=**后台消息中心「话题邀请」里小助手主动推的那条「🔥今日话题 #xxx#（N万人在围观）」卡片**——它是平台"为我推荐"、本次发文带小助手流量扶持标记的那一条，**能抓到就按它写**。⚠️**不要误认成 `_grab_publish_suggest` 抓的"选题推荐轮播列表第一条"**：那是发布页正文区下方的换一换列表，只是补充池，不是"为我推荐的"。取法=现场抓后台（话题邀请/消息中心），认准「话题邀请」分类下带「🔥今日话题 + 小助手流量扶持」的卡片。若当日用户点名了某题且该帧出现，**优先写用户点名条**。
3. **当前帧全是非垂直题 / 抓取失败（退 7）** → 走第八节三级兜底（①现场抓 ②`_grab_publish_suggest --write-pool` ③WebSearch 须标注），兜底仍取能垂直落地的一条。
4. **成稿约束不变**：即便照写"推荐原文"，成稿必须带**信息增量**（自己的判断/真实经历/可核实数据/可操作步骤，四选一），不许把推送原文换个说法复述一遍。
5. **三档统一同步机制（🔴 v1.5＝先甄别「能不能落到本号职场读书视角」再取题，⚠️生效时间＝2026-10-02 起，三档 am/noon/pm 完全同步，覆盖 v1.4「只看流量不卡垂直」）**：
   > 背景（2026-10-02 云明定）：v1.4「只看讨论量最大」把号推去追非垂直大话题（国庆/华为/升旗/明星），CTR 从 09-29 的 8.25% 掉到 10-01 的 1.20%（见 review_history）。大流量 ≠ 可取，先判这条话题**能不能落到 职场技能 / 管理书解读 / 阅读方法 / 考证主池 / 经营数字判断 任一方向**，再决定进不进图文。
   - **数据源**：`node _grab_topic_list.js`（浏览器抓微头条发布页「话题」面板全量，话题名 + 讨论量，落 `debug/topic_list_<DATE>.json`）→ `node topic_rank.js <DATE>`（量/名配对 + **可落地甄别分池** + 三档位次消费，落 `debug/topic_list_<DATE>_ranked.md`；讨论量带千位逗号，如「2,834万」=28,340,000，勿读错位）。
   - **v1.5 双池甄别（核心变更）**：`topic_rank.js` 把全部推荐话题分成两个池——
     · **图文取题池**＝讨论量≥1万 + 未命中排除词 + **可落地**（能写进上述本号方向之一）；am/noon/pm 按位次依次消费**此池**。
     · **微头条补充池**＝讨论量≥1万 + 未命中排除词 + **不可落地**（大众大流量话题）；**只喂微头条**（微头条能吃非垂直、互动效率≈图文10倍），**图文不硬塞**，避免稀释 CTR。
     · **流量只决定「取哪条」（同池内位次），可落地性才决定「这条能不能进图文」**。两条不冲突：先甄别定池，再按流量定位次。
   - **三档位次消费（只从图文取题池取）**：am 取图文池里讨论量最高且 ≥1万 的可用条目；noon 从 am 之后顺延；pm 再顺延。每档从池内 rank1 起**只跳过「命中排除词 / 与已分配档同簇 / 讨论量<1万」**的条目，取第一条可用者。**不可落地的条目不进本池、永不取作图文**（它们进微头条补充池）。全池无可用条目（都被排除词/同簇占满且 <1万）→ 退「为我推荐的」注安主池（第1条）或第三级兜底。
   - **微头条补充池怎么用**：当日非垂直大话题优先留给微头条（各档的 L1 快讯微头条可从这里取，落地成稿时仍套本号职场读书视角做信息增量）；图文主引擎永远优先垂直强池（注安主池 CTR 9~10%）。
   - **人气门槛**：同一取题池内**优先取讨论量 >10万**的条目；>10万 无可用可落地条目时取 ≥1万 的最高一条；全池无 ≥1万 可落地条目才退第三级兜底（①现场重抓 ②`_grab_publish_suggest --write-pool` ③WebSearch 须标注）。
   - **不分区 ≠ 无判断**：排序与展示统一按讨论量降序；**v1.5 加一道「可落地性」甄别（landable 白名单）**，不是"只看流量"，也不是"完全不看流量"——可落地性是取题闸门，流量是池内排序。
   - ⚠️ 这是「选哪条」的筛选补充，**不覆盖安全闸门**（第 6 条），也**不取消差异化矩阵**（同题连推仍需换角度/深度，见第三节）。
   - **生效边界**：v1.5 **2026-10-02 起**对 am/noon/pm 三档生效；2026-09-30~10-01 按 v1.4 发的内容不追溯。
6. 🔴 **安全闸门一律保留、不因新规则放松**：节日过期不能用（`festival_sync.js --check` 退 7 先兜底）、数据真实性禁编造（无出处数字不写）、人物类热点发稿前单独核实现状、首发/广告网络层强制、正文完整性 `BODY_OK`、幂等台账 (date,slot) 判重、humanizer 去 AI 味、头条精选 / 活动流程，全部照旧。

## 一、选题铁律：只有后台推送能定题

1. **选题严格以后台推送为准**，优先级：
   - ① 当日 `invitations_DATE_{slot}.png`（话题邀请）
   - ② 当日 `backend_msg_DATE_{slot}.png`（消息中心）
   - ③ 现场抓取（Playwright 打开 mp.toutiao.com 的「创作灵感 / 话题邀请 / 消息中心」）
   - ④ 前三级都没有 → WebSearch 兜底（须标注"WebSearch 兜底"）
2. **写哪一条由第〇节最高优先级定**（当前帧原文优先）；本条只保留"来源必须以后台推送为准、禁凭记忆定题"。旧的"优先最新+热度最高、写过类似就跳过"已被第〇节覆盖，不再作为筛选依据。
3. **禁止凭记忆或习惯定题**。重复靠信息增量解决（第〇节第 4 条），不靠躲避、也不靠回避。

## 二、双档同步：用状态文件，不靠记忆

### 数据结构 `daily_topic.json`
```
days[YYYY-MM-DD] = {
  am:   { topic, source, heat, core, angle, depth, stance, title, diff },
  pm:   { ... },
  candidates: ["话题A", "话题B", "话题C"]   // 按热度降序
}
```

> **v1.5（2026-10-02 起）＝先甄别可落地性，再取题**：am/noon/pm 三档共用同一张「统一降序 rank 表」（`topic_rank.js` 产出，见第〇节第 5 条），**只从「图文取题池」（可落地话题）按位次消费**；不可落地的大流量话题进「微头条补充池」、只喂微头条，图文不取。本节旧的"am 写候选池 + pm 取另一条"双档逻辑由 rank 表的位次消费替代，下面只保留**登记六要素**与**同题自检**两个硬动作。

### 三档位次消费（替代旧的 am/pm 双档分支）
1. **am 档**：读 `topic_rank.js` 排行表，**只从「图文取题池」**（可落地话题）取**讨论量最高且 ≥1万**的可用条目（跳过排除词/同簇）；不可落地话题自动进微头条补充池、图文不取。
2. **noon 档**：从 am 位次之后**顺延**取下一条可用者（仍只在图文取题池内）；与 am 同题则走差异化矩阵。
3. **pm 档**：再顺延取下一条；同题连推仍走**差异化矩阵**（第三节）换角度/深度/立场。
4. 图文取题池全空（都被排除词/同簇占满且 <1万）→ 退「为我推荐的」注安主池（第 1 条）或第三级兜底（WebSearch）；**不可落地的大流量话题留给微头条**（微头条能吃非垂直，图文不硬塞）。

### 各档发稿前登记（硬动作，脚本自检不变）
- 登记六要素：`node topic_sync.js --date <DATE> --slot <am|noon|pm> --topic '...' --source '<rank 位次+讨论量>' --heat '<讨论量>' --core '...' --angle <角度> --depth <L1|L2|L3> --stance <立场> --title '...'`
- 同题连推附 `--diff '<一句话差异点与递进关系>'`。
- **脚本会自检**：同题且角度+深度全同 → `FATAL_NO_DIFF` 退出码 3，拒绝登记。**被拒就是真被拒，不许绕过，必须换。**

## 三、同题连推的差异化矩阵

同一事件写两篇，**至少换两个维度**（建议三个）：

| 维度 | 可选值 | 说明 |
|---|---|---|
| **切入角度** | 事件经过 / 各方反应 / 原因背景 / 影响趋势 / 争议焦点 | 五选一，两档不得相同 |
| **写作深度** | L1 快讯式简述 / L2 深度解读 / L3 系列纵深 | 见下表 |
| **立场** | 亲历者 / 旁观者 / 反方（反直觉）/ 受益人 / 决策者 | 两档不得相同 |

### 深度层级定义
- **L1 快讯式简述**：载体=微头条 200~500 字。只回答"发生了什么 + 我的一个判断"。不铺背景、不列方法、一个点打透。
- **L2 深度解读**：载体=图文 1000~1500 字，四段结构（标题+引入+分点+收尾）。要有数据/案例/可操作步骤，每个分点至少含一项实质信息。
- **L3 系列纵深**：热点持续多日时使用，跨天递进（如"Day1 事件 → Day2 原因 → Day3 影响"），单天内不用。

### 推荐组合（同题一天两篇）
| 组合 | am | pm | 读者感受 |
|---|---|---|---|
| A（先快后深） | L1 事件经过 · 旁观者 | L2 原因背景 · 亲历者 | "早上知道出了什么事，晚上搞懂为什么" |
| B（先深后反） | L2 影响趋势 · 亲历者 | L1 争议焦点 · 反方 | "早上给方法，晚上给反面提醒" |
| C（双深换角） | L2 原因背景 · 决策者 | L2 各方反应 · 受益人 | 适合超级大热点，两篇都做深度但视角对立 |

> ⚠️ 组合 C 要求两篇的核心观点**不能互相抄结论**，必须各自成立、互补而非重复。

## 四、输出标注（每篇成稿必带）

每篇成稿开头/汇报里必须给出五要素，缺一项视为未交付：

```
【时段】am / pm
【来源话题】<后台推送原文话题名，含围观量/扶持标记>
【核心观点】<一句话，本文独有结论，不得与另一档雷同>
【切入角度】事件经过 / 各方反应 / 原因背景 / 影响趋势 / 争议焦点
【深度层级】L1 快讯式简述 / L2 深度解读 / L3 系列纵深（+ 字数与载体）
```

**同题连推时另附一句话**，说清差异点与递进关系，格式：
> **两篇差异**：am 讲「为什么必须考」（L1·判断），pm 讲「48 天怎么排」（L2·方法）——先建立动机，再给可执行方案，读者从"要不要做"走到"怎么做"。

## 五、语言与信息量要求

- **口语化、观点鲜明、有信息增量**。
- 禁空泛复述：不许把推送原文换个说法再写一遍；每篇必须至少有一条**推送里没有的东西**——自己的判断、真实经历、可核实的数据、可操作步骤，四选一。
- 禁观点雷同：两篇的核心句不得是同一个意思的不同说法（自检方法：把两篇的核心观点各写一句话放一起，如果可以合并成一句，就是雷同，重写）。
- 禁标题党：标题可以有钩子，但正文必须兑现标题承诺；不写"震惊""速看""终于"。
- 沿用原有安全红线：数据不得编造（无来源不写）、人物类热点发稿前单独核实人物现状、不碰挂靠/包过/收入承诺。

## 六、执行顺序（放进发布流程，位于"数据复盘"之后、"写稿"之前）

> **v1.4 三档统一同步（2026-09-30 起，只看流量、不卡垂直）**：推荐话题统一降序 + 三档位次消费，见第〇节第 5 条；脚本链路 = 第 2.5 步（每日先 `_grab_topic_list.js` 爬数据、再 `topic_rank.js` 排名）。

```
1. 数据复盘（check_backend.js）
2. 抓后台热点 → 得到候选池（按热度降序）
   2.5 node _grab_topic_list.js                # 抓话题面板全量（话题+讨论量）落 debug/topic_list_<DATE>.json
   2.6 node topic_rank.js <DATE>               # 统一降序 + 三档位次消费（只看流量·跳过排除/同簇/<1万，不卡垂直）落 debug/topic_list_<DATE>_ranked.md
3. node topic_sync.js --date <DATE>            # pm 档：读 am 已用角度；am 档：看昨天残留
4. 选本档话题：按第 2.6 步 rank 表位次消费（am/noon/pm 依次顺延，同题走差异化矩阵）
   ※ 注安主池流量以 hot_push_grab 的「为我推荐的」为准（面板「最近使用」里的小量数≠当日扶持量，勿混用）
5. node topic_sync.js --slot <am|pm> ...       # 登记六要素（同题自检在这里拦）
6. 写稿（图文 L2 / 微头条 L1）→ humanizer
7. 封面 → 发布 → 核验（原流程不变）
8. 汇报附五要素 + 差异说明 + 本档 rank 位次与跳过说明
```

## 八、节日/时令主题时效性（v3.4 新增）

> 解决的问题：节日主题（如教师节）只在当天有效，过期必须自动下线，不得继续出现在创作灵感候选池、不得被再次选中。

### 1. 日期判断方式

- **一律用北京时间（UTC+8）**，与 `topic_sync.js` 的 `bjNow()` 完全同口径：
  ```js
  new Date(Date.now() + 8 * 3600 * 1000).toISOString().slice(0, 10)
  ```
- 节日定义放在 `festival_topics.json`，**不在代码里写死**：
  - `date`：生效首日（`YYYY-MM-DD`）
  - `window_days`：连续生效天数，默认 `1`（即仅当天）
  - `annual`：每年固定公历日期（`MM-DD`），用于次年自动续期
  - `match_keys`：用于从候选池识别该节日主题的关键词
- 判定：`date ≤ 今天 ≤ 结束日` → **生效**；`今天 > 结束日` → **已过期，自动下线**。

### 2. 下线处理方式：**隐藏 + 替换，严禁置空**

| 方案 | 是否采用 | 说明 |
|---|---|---|
| **隐藏** | ✅ 采用 | 过期条目从「当前候选池」剔除，不再参与选题；原配置条目标 `status=expired` 保留做审计留痕 |
| **替换** | ✅ 采用 | 过滤后若候选池不足，用常规抓取结果顶上 |
| **置空** | ❌ 禁止 | 置空会导致自动化空转或误用旧题，属事故级风险 |

### 3. 跨天切换兜底（三级）

过滤后候选池为空 → `festival_sync.js` 返回**退出码 7**，按序兜底：

1. **现场抓取**：创作灵感 / 话题邀请 / 消息中心（Playwright，见第一节 ③）
2. **推荐池**：`node _grab_publish_suggest.js --write-pool`
3. **WebSearch 兜底**：须在汇报标注"WebSearch 兜底"

> 🔴 **硬拦截**：任何情况下都不得使用已过期的节日主题，**即使候选池为空**。宁可走 WebSearch 兜底，也不复用过期内容。

### 4. 命令与退出码

```bash
node festival_sync.js --today                    # 列出今天生效 / 已下线的节日
node festival_sync.js --prune                    # 剔除候选池中的过期条目（写盘）
node festival_sync.js --check                    # 自检，dryRun 不落盘（供 topic_sync 只读模式调用）
node festival_sync.js --date 2026-09-11 --today  # 指定日期预演
```

| 退出码 | 含义 |
|---|---|
| 0 | 正常 |
| 2 | 节日配置损坏或参数错误（fail-loud，禁止带病运行） |
| 7 | 过滤后候选池为空，**必须走三级兜底重新检索** |

`topic_sync.js --date <DATE>`（读档）会自动调用 `--check` 并附 `--- FESTIVAL ---` 段，选型前必读。

### 5. 次年自动续期

过期且带 `annual` 的条目 → 自动**追加**下一年空壳条目：
- `topics` 留空 —— 届时**须重新检索当年素材，不得沿用旧内容**（去年的政策/事件/数据今年已失效）
- 原条目**永不改写**，只标 `status=expired`

> ⚠️ 显式传 `--date`（测试/补跑）时**只做剔除，不写状态、不续期**，防止用未来日期执行时污染真实配置。

### 6. 执行顺序（对第六节的修订）

```
1. 数据复盘（check_backend.js）
2. 抓后台热点 → 得到候选池（按热度降序）
```

## 九、创作灵感＝创作活动池，按垂直领域筛选（v3.5 新增）

> 解决的问题：此前选题只看「话题邀请」，**从未进过「创作灵感」**。实测发现「创作灵感」不是选题推荐，而是
> **官方创作活动池** `mp.toutiao.com/profile_v4/activity/task-list`，全站约 **2800 个活动**，左上角有
> 「垂直领域」下拉可按领域筛选（本号：职场 128 个 / 教育 186 个）。这是除话题邀请之外**第二个官方流量池**。

### 1. 为什么必须固化

| 事实 | 数据 |
|---|---|
| 活动池总量 | 2800 个（此前只从「话题邀请」看到 1 条注安，连推 7 天） |
| 本号可见 | 职场域 128 + 教育域 186 |
| 2026-09-10 首次抓取即挖到 3 个从未用过的池 | 你问我答（14万·11.3万人）/ 以书之名（1万·3.3万人）/ 探寻人工智能（10万·9.3万人） |
| 直接后果 | 注安同题连发 7 天 → 题材疲劳 → 09-09 展现断崖 -89% |

### 2. 领域与排除策略都放配置，不写死在代码

`inspiration_pool.json`：

| 字段 | 作用 |
|---|---|
| `fields` | 本号垂直领域，顺序＝抓取优先级，默认 `["职场","教育"]` |
| `pin` | 人工置顶的活动名（如新挖到的池优先消费），用过即自动退场 |
| `exclude_keys` | 排除词，命中活动名或描述即剔除（打卡季 / 幸运签 / 晒家乡 / 对联 / 高考 / 穿搭 …） |
| `activities` | 抓取结果，含 `joined_num`（参与人数，用于排序）、`used`（已用标记） |

> ⚠️ **不加排除词就会被热度绑架**：默认按参与人数降序时，Top10 全是「高考幸运签 235 万 / 冬日打卡季 170 万 / 对对联 166 万」这类与职场读书无关的活动。排除词是必须的，且要随活动池变化维护。

### 3. 命令与退出码

```bash
node inspiration_sync.js --grab                      # 现场抓取（需浏览器，一天一次，am 档执行）
node inspiration_sync.js --grab --fields 职场,教育     # 显式指定领域
node inspiration_sync.js --check --top 5             # 只读推荐，不联网（am/pm 每档必跑）
node inspiration_sync.js --use --name '你问我答' --slot am   # 发布成功后标记已用
node inspiration_sync.js --unuse --name '你问我答'    # 撤销
node inspiration_sync.js --list                      # 全量列表（含已用）
```

| 退出码 | 含义 | 处理 |
|---|---|---|
| 0 | 正常 | — |
| 2 | 参数或池配置损坏（fail-loud） | 先修 `inspiration_pool.json` 再选题 |
| **3** | **抓取失败**（页面没打开 / 下拉未命中 / 登录态失效） | **必须告警**，不许当成"没有活动"；走三级兜底 |
| **7** | `--check` 无可推荐条目（从未抓取 / 全已用 / 全被排除） | 先 `--grab`；仍失败走三级兜底 |

> ⚠️ **退出码 3 和 7 完全不同**：3＝脚本没抓到（可能是登录态挂了，要人工看），7＝池子真的空了（要补新料）。混淆会导致漏报登录态失效。

### 4. 抓不到时的三级兜底（与第八节同源）

1. **现场重抓**：换 `CDP_PORT` 重试一次（实测 `connectOverCDP: read ECONNRESET` 是本机已知抖动，换端口即恢复）
2. **推荐池**：`node _grab_publish_suggest.js --write-pool`
3. **WebSearch 兜底**：须在汇报标注"WebSearch 兜底"

### 5. 与选题流程的关系

- 活动池是**补充池，不是主池**：话题邀请仍是第一优先级，但**选题时必须同时看活动池**，不许只看话题邀请就定题。
- `topic_sync.js --date <DATE>`（读档）会自动调用 `--check --top 5`，输出 `--- INSPIRATION ---` 段，**选型前必读**。
- 选中某活动并发布成功后，必须 `--use --name '活动名' --slot <am|pm>` 回写，否则下次还会推荐同一个。
- 排序规则：`pin` 置顶 → 其余按 `joined_num` 降序。

## 十、非注安方向优先级（2026-09-19 数据复盘结论）
